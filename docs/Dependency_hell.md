### 1.1 What must be true every time

1. **Env var** (WSL2 only): `VLLM_WSL2_ENABLE_PIN_MEMORY=1`, set before Python starts or at the top of the script before importing `vllm`. Without it vLLM 0.24.0 fails with `RuntimeError: UVA is not available` (row 23). `spike_rollout_func.py` already sets it.
2. **Override file** when (re)installing anything into this venv, because Unsloth's declared caps are stale (row 25). Contents of `overrides.txt`:
   ```
   trl==0.29.1
   transformers==5.17.0
   ```
   Then install with: `uv pip install --override overrides.txt <full package list>`. Always the FULL list plus the vLLM wheel URL, never one package (rule in section 2).
3. **vLLM wheel URL** (do not let the resolver replace it with the PyPI build):
   `https://github.com/vllm-project/vllm/releases/download/v0.24.0/vllm-0.24.0+cu129-cp38-abi3-manylinux_2_28_x86_64.whl`
4. `rollout_func` must return exactly one trajectory per prompt it receives (row 27).

## 2. Why it kept breaking (read before installing anything)

1. **`pip check` and `--dry-run` only compare declared version ranges.** They cannot see that package A imports a function that package B removed. Rows 14, 15 and 19 were all invisible to both. The only real test is to import the packages and run the actual call (`FastLanguageModel.from_pretrained(fast_inference=True)`, then `get_peft_model`, then a 2-step train).
2. **Unpinned dependencies drift to "newest" on every fresh resolve.** `torchao`, `peft`, `bitsandbytes` and others are unbounded upstream, so each new venv picked versions the rest of the stack was never tested with (rows 18, 19).
3. **Unsloth's declared caps lag behind its code.** Its metadata said `trl<=0.24.0` and `transformers<=5.5.0`, while its source already contains code for "TRL >= 0.28" and transformers 5.x (rows 2, 21, 25). When metadata and source disagree, test at runtime, and record the override explicitly.
4. **The layers are locked together.** vLLM pins torch, torchvision, xformers and a transformers floor. Changing vLLM changes all of them (rows 11, 17). Never upgrade one of them alone.
5. **WSL2 changes defaults.** vLLM disables pinned memory on WSL2, and its newest model runner needs it (row 23). Bugs that look like "Blackwell" or "quantization" problems may be platform defaults. Read the source line that raised the error before theorising.
6. **Never install one package into a resolved venv.** Use one `uv pip install` with the full list (and `--override` where needed), then `pip check`, then import-test.
7. **Read the traceback's real error text before choosing a fix.** In row 27 the error was a batch-size mismatch in my own script, not a weights format problem. In row 23 the cause was a WSL default.

### Options considered and rejected

- **Ditching vLLM for llama.cpp.** TRL 0.24.0, TRL 0.29.1 and Unsloth's `rl.py` contain 0 references to llama.cpp (Unsloth uses it only to export GGUF files). GRPO needs samples and logprobs from the current policy at every step, which would mean rebuilding weights into a new format each step. vLLM was working on the RTX 5090 in two different versions (0.10.2 and 0.24.0), so the Blackwell worry was not confirmed by our tests.
- **`model.save_pretrained_merged(..., "merged_16bit")`** (from Unsloth's vLLM deployment page). That is for exporting a trained model to serve it. It does not address the tensor-size error in row 27.
- **Compat shim for `vllm.lora.models`** (row 15): it only reveals the next missing symbol.
